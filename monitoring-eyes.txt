# Monitoring Eyes — Architecture & Design Document

> CI/CD 파이프라인의 KPI 자동 모니터링 및 이상 탐지 시스템

---

## 1. Problem Statement

### 배경
대규모 통신 SW의 CI/CD 파이프라인에서는 매일 수십 개의 Stability/Capacity/Robustness 테스트가 빌드별로 실행된다. 각 테스트는 수십 개의 KPI(CPU, Memory, Throughput, Latency, Packet Loss 등)를 산출하며, 빌드 간 이 수치의 변화를 감지하는 것이 SW 품질 관리의 핵심이다.

### 문제
- 수동 감시: 엔지니어가 매일 포탈에서 결과를 하나씩 확인 → 시간 소모, 누락 발생
- Threshold 관리: KPI마다 정상 범위가 다르고, SW 변경에 따라 범위 자체가 drift
- 분류 어려움: 실패 원인이 SW 결함인지, 노드 HW 문제인지, 테스트 환경 문제인지 분류 필요
- Improvement도 이상: 성능이 "좋아진" 것도 기능 오작동의 부작용일 수 있음

### 목표
1. KPI 변화 자동 감지 (degradation + improvement 모두)
2. 빌드 간 비교 자동화 (component version 변경 추적 포함)
3. 실패 원인 분류 지원 (노드 문제 vs SW 결함)
4. KPI threshold 자동 튜닝
5. AI agent와 연동하여 자연어 기반 분석 지원 (MCP)

## 5. Core Algorithms

### 5.1 KPI Anomaly Detection (Rule-based)

```python
# 의사 코드
def check_kpi_anomaly(kpi_name, current_value, history_values):
    rule = get_rule(kpi_name)  # tunning_rule에서 규칙 로드
    
    if rule.type == "absolute":
        # CPU 계열: ±2 절대값
        range_min = min(history_values) - rule.margin
        range_max = max(history_values) + rule.margin
        
    elif rule.type == "relative_percent":
        # Memory 계열: ±2%
        baseline = mean(history_values)
        range_min = baseline * (1 - rule.margin_pct)
        range_max = baseline * (1 + rule.margin_pct)
        
    elif rule.type == "ratio":
        # Packet Loss: 특수 공식
        # (loss_total * 5) / dallas_sent_total
        pass
    
    if current_value < range_min:
        return "IMPROVEMENT"  # ← 이것도 anomaly로 분류
    elif current_value > range_max:
        return "DEGRADATION"
    else:
        return "NORMAL"
```

### KPI 카테고리별 규칙

| 카테고리 | Margin | 방식 | 예시 KPI |
|----------|--------|------|----------|
| CPU | ±2 (절대) | absolute | background_cpu, egress_cpu |
| Memory (Private) | ±2% | relative | shmem_avg, sysmon_mem |
| Memory (UPP) | ±5% | relative | upp_mem_avg (jemalloc 고려) |
| Throughput | ±2% | relative | total_pps, capacity_Gbps |
| Session | ±1% | relative | PFCP_sessions |
| Packet Loss | 특수 공식 | ratio | E2E loss, UPF loss |

### 5.2 Auto Tuning Algorithm

```python
def auto_tune_kpi(tc, kpi_name):
    # 1. 최근 3빌드에서 해당 KPI 값 수집
    recent_values = get_last_n_values(tc, kpi_name, n=3)
    
    # 2. 평균 계산
    baseline = mean(recent_values)
    
    # 3. 카테고리별 규칙 적용
    rule = get_rule(kpi_name)
    if rule.type == "absolute":
        new_min = baseline - rule.margin
        new_max = baseline + rule.margin
    elif rule.type == "relative_percent":
        new_min = baseline * (1 - rule.margin_pct)
        new_max = baseline * (1 + rule.margin_pct)
    
    # 4. Verdict checkpoint 파일 업데이트
    update_checkpoint_range(tc, kpi_name, new_min, new_max)
    
    # 5. verdict-analyze 실행하여 검증
    run_verdict_analyze(tc)
    
    return {
        "kpi": kpi_name,
        "old_range": get_current_range(tc, kpi_name),
        "new_range": (new_min, new_max),
        "based_on": recent_values
    }
```

### 5.3 CI Failure Classification

```python
def classify_failure(tc, build, node, checkpoint):
    """
    실패 원인 분류:
    1. Node-Specific: 같은 빌드에서 특정 노드만 실패
    2. Build-Specific: 같은 빌드에서 모든 노드 실패 → SW 결함
    3. Intermittent: 간헐적 → 환경/타이밍 이슈
    """
    
    # 같은 빌드, 다른 노드 결과 확인
    same_build_results = get_results(tc, build, all_nodes=True)
    
    # 같은 노드, 다른 빌드 결과 확인
    same_node_results = get_results(tc, all_builds=True, node=node)
    
    if all_fail(same_build_results):
        # 모든 노드에서 실패 → SW 결함 가능성 높음
        return "BUILD_ISSUE", "PCTR"
        
    elif only_this_node_fails(same_build_results, node):
        # 이 노드만 실패 → 노드 HW 문제
        if is_consecutive(same_node_results, threshold=3):
            return "NODE_ISSUE", "PCGW"
        else:
            return "INTERMITTENT", "MONITOR"
            
    else:
        return "UNKNOWN", "INVESTIGATE"
```

### 5.4 Component Version Diff

```python
def compare_component_versions(build1, build2):
    """
    두 빌드 간 component version 변경 추적
    → KPI 변화의 원인 commit 범위를 좁히는 데 사용
    """
    info1 = load_build_info(build1)  # _build_info/Build1.json
    info2 = load_build_info(build2)
    
    changes = {}
    tracked_components = [
        "PC UP Common Base",
        "PC UP Data Plane",
        "PC UP PFCP Endpoint",
        "Timer Wheel",
        "Key Value Database RD Replicator",
        "IPOS SDK", "CBOS", "DPI APR",
        # ... 20+ components
    ]
    
    for comp in tracked_components:
        v1 = info1.get(comp)
        v2 = info2.get(comp)
        if v1 != v2:
            changes[comp] = {"from": v1, "to": v2}
    
    return changes
```

## 9. Decision Tree: Anomaly Classification

```
KPI 변화 감지됨
    │
    ├── Degradation (값 증가/감소 방향이 나쁜 쪽)
    │   ├── 모든 노드에서 발생? → SW 결함 가능성 → PCTR
    │   ├── 특정 노드만? → 노드 문제 → PCGW
    │   └── 간헐적? → 모니터링 지속
    │
    └── Improvement (값이 "좋아진" 방향)
        ├── Component version 변경 있음?
        │   ├── 의도된 최적화 commit 있음? → Tune range
        │   └── 없음? → 기능 오작동 가능성 → PCTR
        └── Version 변경 없음? → 환경 변화 확인
```

| File-based storage (DB 없음) | 인프라 의존성 최소화, git으로 이력 관리 가능 |
| MCP 프로토콜 채택 | AI agent가 직접 tool을 호출하여 분석 → 사람의 질의를 자동 처리 |
| Rule-based 탐지 우선 | 데이터 양 제한적, false positive 최소화 우선 |
| 단일 파일 MCP 서버 (60KB) | 빠른 개발, 배포 단순화 (trade-off: 유지보수성) |
| ONNX 모델 | GPU 불필요, 경량 서버에서 inference 가능 |
| Cron 기반 수집 | 실시간 불필요 (테스트는 수시간 소요), 단순 안정적 |
